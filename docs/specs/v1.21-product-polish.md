# AROUND v1.21 — Product Polish Specification

## Status
Ready for implementation review.

## Goal

v1.21 is a consolidation release.

Do **not** add a major new product concept.

The goal is to make the current Trip Planner feel more intentional, consistent and trustworthy after the major Quick Add and Smart Planning work.

## Scope

### P1 — Plan Check: offer both adjacent STAY repairs

#### Current behavior
When one or more nights are uncovered, Plan Check identifies the missing date range and may offer to extend the previous STAY.

#### Desired behavior
When the uncovered range sits between two existing STAY segments, evaluate both adjacent repairs:

1. extend the previous STAY through the gap
2. start the next STAY earlier to cover the gap

Example:

```text
Hotel Unterwirt
19.09. → 20.09.

OPEN
20.09. → 21.09.

Winklmoos SonnenAlm
21.09. → 22.09.
```

Plan Check should be able to offer:

- `HOTEL UNTERWIRT VERLÄNGERN`
- `SONNENALM FRÜHER STARTEN`
- `STAY HINZUFÜGEN →`
- `KEINE UNTERKUNFT NÖTIG`
- `SPÄTER ENTSCHEIDEN`

Only show an adjacent repair if that repair is valid and does not create an overlap.

#### Acceptance criteria
- prior-adjacent STAY is detected correctly
- next-adjacent STAY is detected correctly
- either, both or neither repair action may be shown depending on state
- clicking previous extension updates only the appropriate stay range
- clicking next earlier-start updates only the appropriate stay range
- no duplicate stay is created
- no overlap is silently created
- current add/new/no-stay/later actions still work

---

### P2 — Flexible stops show duration when known

#### Current behavior
A flexible item may show its daypart but can lose the editorially known duration in the compact planner presentation.

#### Desired behavior
If `durationMinutes` exists for a flexible item, surface it compactly.

Preferred visual hierarchy example:

```text
NACHMITTAG · CA. 4 STD
WINKLMOOS-ALM
```

or an equivalent layout consistent with the existing planner grid.

Do not turn flexible items into fixed-time items.

#### Acceptance criteria
- flexible stop with duration shows duration
- flexible stop without duration remains clean
- fixed stop display is unchanged
- mobile remains readable
- intermediate planner layout remains stable

---

### P3 — Plan Check semantic state for “later”

#### Desired behavior
`SPÄTER ENTSCHEIDEN` must not make the trip appear fully accommodation-complete.

It should represent an unresolved planning state.

`KEINE UNTERKUNFT NÖTIG` is intentional and may count as resolved.

#### Implementation constraint
Do not introduce a new Supabase migration unless the current model cannot represent the distinction.

First inspect existing fields / stay exemptions / readiness state and reuse the current model if possible.

If a migration is genuinely required, stop and report before changing the schema.

#### Acceptance criteria
- no-stay-required remains intentionally resolved
- later-decision remains unresolved in readiness messaging
- existing trips do not break

### P5 — Microcopy consistency

Review visible planning terms for consistency.

Preferred vocabulary:
- FIXPUNKT
- FLEXIBEL
- ZEITFENSTER
- TERMIN / TEE TIME / RESERVIERUNG where semantically appropriate
- DAUER
- STATUS
- NOTIZ
- OFFEN
- ANGEFRAGT
- RESERVIERT

Do not rename established concepts without a clear reason.

---

## Out of scope

Do not implement in v1.21:
- recommendation engine
- maps
- route optimization
- booking integrations
- payments
- new authentication flows
- Contao integration
- large Sanity content model redesign
- Supabase schema redesign
- AI itinerary generation

## Data migrations

Expected:
- no Supabase migration
- no Sanity migration

If implementation proves otherwise, stop and report the need before modifying schema.

## Required implementation report

After implementation, Claude Code should report:

1. changed files
2. behavior implemented for P1–P5
3. TypeScript result
4. build result
5. whether any migration/schema change occurred
6. responsive states manually reviewed
7. known remaining issues

## Definition of done

v1.21 is complete when:
- P1 and P2 are implemented
- P3 semantics are preserved/clarified without data regression
- P4 QA has been performed
- P5 microcopy does not regress
- TypeScript passes
- `npm run build` passes
- no unapproved migration occurred
